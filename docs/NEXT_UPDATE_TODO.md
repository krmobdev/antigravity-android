## 1. Согласованные пользовательские требования (будущая работа)

### A. Новая модель прочтения результатов — отдельная будущая задача

**Принято пользователем:** получение ответа, завершение агента и просто открытый разговор **не доказывают прочтение**.

- Если весь ответ умещается на экране, для признания его прочитанным необходимо осознанное взаимодействие пользователя **после появления** ответа.
- Если ответ длинный, учитывать **фактический просмотр всего содержимого от начала до конца**. Простое касание длинного ответа недостаточно.
- Открытие разговора, переход по Android-уведомлению и событие `onResume` сами по себе не означают прочтение.
- Блокировка экрана, сворачивание, перезапуск приложения и сбой не должны автоматически устанавливать `read`.
- Желательно сохранять прогресс просмотра при прерывании (пожелание, не согласованный технический механизм).
- Предусмотреть отдельное ручное управление отметкой прочтения.

**Не решено:** что именно считать «осознанным взаимодействием», как подтверждать полный просмотр и хранить прогресс. Техническую архитектуру, обработчики жестов, серверный протокол и UX пока **не проектировать**. Начать будущую работу с согласования требований и проверки поведения upstream.

**Предыдущее исследование:** [deferred-read-unread-v24.md](deferred-read-unread-v24.md). Экспериментальный readfix `432228d` отменён коммитом `f33e724`; **не возвращать его** в текущую интеграцию. Синяя точка непрочитанности и `Working` — независимые состояния.

### B. Очистка уведомлений после доказанного прочтения — зависимая будущая задача

**Предварительное пожелание пользователя**, реализация только после определения надёжной модели из пункта A:

- Оставлять уведомления о непрочитанных результатах в Android-шторке.
- После **подтверждённого** прочтения рассмотреть автоматическое удаление уведомления соответствующего разговора через **5–10 минут**.
- Смахивание уведомления не означает прочтение.
- Удаление уведомления не меняет `read/unread`.
- Постоянное уведомление `Core running` не затрагивать.
- Разные разговоры и их уведомления обрабатывать независимо.

**Не решено:** точный интервал в пределах 5–10 минут, подтверждающее событие и правила восстановления после перезапуска. Не менять текущие Android notification channels или обработку completion queue.

### B.1. Показывать последний этап работы агента в Android-шторке — новая задача

**Запрос пользователя от 21.10.2026:** во время длительного выполнения сейчас видно лишь общее «Агент выполняет задачу» и индикатор прогресса; непонятно, **чем агент занят в данный момент**. Нужно показывать **последний подтверждённый этап выполнения конкретной задачи** непосредственно в её текущем уведомлении, в том числе когда приложение свёрнуто или экран заблокирован.

- Для каждой активной беседы/задачи отображать короткую, понятную строку **последнего реально полученного этапа**, например «Читает исходники», «Редактирует файлы», «Запускает тесты», «Анализирует результат» — только если соответствующий этап действительно подтверждён событиями Core.
- При переходе к следующему этапу обновлять **существующее уведомление той же задачи**, а не создавать новое уведомление на каждый шаг; сохранять название беседы и переход по нажатию.
- При нескольких одновременных агентах показывать **их собственные** последние этапы, без смешения между беседами.
- При отсутствии достоверной информации об этапе выводить нейтральное «Агент выполняет задачу», **не угадывать** текущую работу по таймеру или модели.
- Обновлять текст при работе в фоне и после восстановления WebView/подписки на события; не показывать устаревший этап другой задачи. Учитывать ограничения Android по частоте уведомлений, не спамить шторку.
- Не выводить секреты, токены, полные запросы, содержимое приватных файлов и длинные технические логи в уведомление на экране блокировки: по умолчанию краткое безопасное описание.
- Корректно переключать статус «Работает» → «Завершено/Ошибка/Отменено», не возвращать устаревший Working после подтверждённого завершения; не ломать завершения, FIFO уведомлений, read/unread и постоянное Core running.

**Критерии приёмки:** задача проходит несколько настоящих этапов → в шторке меняется текст последнего этапа; сворачивание/блокировка не замораживают обновления; при параллельных заданиях сообщения остаются раздельными; после завершения активный статус не зависает. Добавить автоматические тесты последовательности событий, дублей, переподключения и завершения.

**Пока не реализовывать:** сначала проверить, какие достоверные этапы доступны в существующем native/Core agent tracker без новых опасных интерпретаций и насколько они подходят для публичного уведомления.

## 2. Требует исследования, не подтверждено как дефект

### C. Длинные пользовательские сообщения в разговоре

**Наблюдение пользователя:** при испытании с завершением `30/30` около 23:13:56 и 23:14:04 длинный исходный промпт отображался в карточке с закруглёнными углами, частично обрезанным текстом и внутренней тенью/градиентным затемнением. Это **не доказанный фриз** WebView или Hca.

Для следующего обновления:

- Проверить, можно ли прокручивать текст внутри карточки и как работает прокрутка.
- Выяснить, существует ли раскрытие полного сообщения.
- Оценить, требуется ли более понятный визуальный признак свёрнутого содержимого.

**Нет решения менять UI:** прежде установить, штатная ли это функция или реальный дефект. Не относить к Hca без доказательств.

### CI/CD release signing — November 2026

Решение: сейчас GitHub Actions **не запускать** (месячный лимит исчерпан). Workflow оставлен только для будущего ручного запуска, job временно заблокирован до настройки подписи. После восстановления лимита:

1. Использовать **уже созданный постоянный** release keystore после подтверждения резервной копии, не генерировать новый.
2. Добавить секреты GitHub: `AGY_RELEASE_KEYSTORE_BASE64`, `AGY_RELEASE_STORE_PASSWORD`, `AGY_RELEASE_KEY_ALIAS`, `AGY_RELEASE_KEY_PASSWORD`.
3. Изменить workflow так, чтобы сборка подписывалась этим ключом, а не публичным debug.keystore; вернуть тесты и включать автоматизацию только после проверки.
4. Сверить SHA-256 сертификата нового APK с сертификатом первого релиза; проверить обновление с повышенным `versionCode` поверх первого APK без потери данных.
5. Только после проверки разрешить автоматические триггеры публикации.

Это будущий план, а не действующее CI/CD.

## 3. Необязательные, низкий приоритет

### D. Уведомления и FIFO

- **Вибрация:** при завершении пользователь не почувствовал вибрацию. В будущем проверить пользовательские настройки Android, системные ограничения и текущие параметры notification channel **перед выводом о дефекте**. Сейчас каналы не изменять.
- **Реальная задержка FIFO 5 секунд:** программные тесты подтверждают интервал и защиту от дублей. В пользовательском испытании два Core-завершения 22:19:03 и 22:19:18 естественно разделяли около 15 секунд, поэтому реальная очередь не задерживала второе уведомление. Дополнительное реальное испытание столкнувшихся по времени завершений — необязательное будущее подтверждение, а не блокер принятого сценария.

## Границы текущего релиза

- **Реальные положительные проверки:** два одновременных агента и раздельные нативные завершения, фоновые уведомления, сохранение непрочитанности после запуска обычным ярлыком, отсутствие застывшего `Working`, два восстановления работающего разговора после паузы.
- **Программные проверки:** пятиисекундное ожидание FIFO при пересечении событий, точная переподписка transport в Hca, восстановление NDa после stream teardown.
- Ни одна задача выше не включена в три исходных патча v2.4.0. Изменения только после отдельного согласования будущего обновления.
