## Overview

Long-running coding tasks should not lose their completion notification or leave a misleading “Working” indicator when Android suspends an Activity. This release incorporates three deliberately scoped reliability fixes on top of upstream **v2.4.0**, preserving the existing Core, Gateway, authentication flow and application functionality.

Our fork ships under the separate Android application ID **`com.krmobdev.antigravity`**. It can coexist with upstream `com.agy` and the integration test app `com.agy.dev`. It has its own app data and sign-in state; installing this package **does not import conversations or credentials** from the other apps.

## What's New

### 1. Native Agent Notifications

WebView JavaScript may pause or lose an observation stream when Android backgrounds or stops the Activity. Task completion must not depend on a live browser tab.

A service-owned **NativeAgentStateObserver** independently subscribes to the real Core agent-state stream for observed conversations. It tracks each conversation separately and recognizes completion only on an authoritative **`IDLE` with `fullyIdle=true`**. Notifications are posted using Android NotificationManager rather than scraping conversation text or guessing from the UI.

- Distinct completion notifications for concurrent conversations, even when titles are identical.
- Notification taps navigate to the matching conversation.
- Separate notification channels for progress, in-chat completion and background completion.
- A persistent, deduplicating completion queue; foreground-visible chats do not cause redundant heads-up banners.
- Five-second spacing for queued heads-up alerts, with bounded persistence and retry when delivery is temporarily unavailable.
- Native observation continues while the Activity is stopped, independent of WebView rendering.

### 2. Hca Stream Recovery

Returning from the background can leave a stale WebView observation transport waiting indefinitely, even while Core continues the task.

When the host sends `agy:host-resume`, **Hca** aborts only the stale **observation transport**, then re-subscribes and rehydrates the current Core state. It does **not** cancel the running agent, its parent lifecycle controller or its task.

This restores progress and completion in the open conversation after lock/unlock and background/foreground transitions without relaunching the job or duplicating its answer.

### 3. NDa / Sidebar State Reconciliation

A conversation summary can temporarily retain a stale “working” status after Core has already reported completion. The sidebar now refreshes its summary feed after the host resumes and reconciles stale status using **Core-confirmed** completion, connected to the actual upstream v2.4 React sidebar components.

- A genuinely running agent continues to display **Working**.
- A completed agent does not retain an obsolete **Working** label.
- Other conversations retain their own independent statuses.
- New genuine RUNNING events take precedence over older completion evidence.
- **Blue unread-result dots are separate from Working.** The existing upstream read/unread system is untouched.

## Validation — real Android testing

The three integration fixes were extensively tested on an actual Android phone on **20 October 2026**, using `com.agy.dev`:

- An agent completed while the Android Activity was stopped; native completion and a correct conversation deep link were observed.
- **Two Core agents ran simultaneously** for approximately 45.5 seconds. Both completed while the Activity was stopped; Android showed **two independent completion notifications**, with no duplicate finish posts or native stream errors.
- After reopening through the normal launcher **without viewing either conversation**, both finished conversations retained their unread dots and neither showed an obsolete Working indicator.
- A longer Termux-driven test used **ten sequential `sleep 10` operations**, with progress from `10/100` to `100/100`. The user locked/unlocked twice, resumed work, completed the task and saw exactly one final response.
- A separate long-task test ended at **`30/30`, `ГОТОВО`**. Activity pause/stop/resume and native Core completion were independently observed; its sidebar changed from Working to a normal time label. This second test is **not** described as a 50- or 100-second run.

**Scope distinction:** Those multi-agent and long-duration results come from the verified **dev integration build**. The new separately identified, release-signed APK has its own installation and startup verification, which must be completed before publishing it as stable. Do not treat Dev test results as independent full end-to-end release-package tests.

## Verification and integrity

Source-level and local Android checks cover:

- Java: `AgentTaskTracker`, NativeAgentStateObserver state handling, FIFO persistence/cooldown/retry/dedup, ConnectRPC framing and Gateway authentication.
- JavaScript/React: real upstream v2.4 sidebar component code, state isolation, Hca transport-only resubscribe and rehydration, NDa refreshed snapshots and rejection of stale stream frames.
- Python: version-pinned staging, builder/configuration and APK contents, while keeping upstream `web/main.js` unchanged.
- Android: local Termux build, zip alignment, `apksigner verify` (v2/v3), distinct package ID and `android:debuggable=false`.

**Limits of evidence:** Real Core completions occurred approximately **14.8 seconds apart**, so the **five-second FIFO spacing** was exercised by controlled and deterministic tests, not by two colliding real Core completions. The exact JavaScript Hca/NDa re-subscription sequence was programmatically tested; on-device observations establish the visible recovery and native lifecycle transitions. **GitHub Actions did not run**: the monthly Actions allowance was exhausted, and automatic release triggers have been deliberately disabled.

## Installation and upgrades

1. Download `Antigravity-Android-v2.4.0-kr1.apk` and `SHA256SUMS.txt` from this fork's GitHub Release once it is published.
2. Verify the downloaded APK using the SHA-256 sum.
3. On an **ARM64 (arm64-v8a) Android device, Android 7.0+ (API 24+)**, allow the chosen file manager/browser to install APKs and install the file.
4. Open **Antigravity KR** and sign in using the browser as needed. This fork has separate app data and permissions; allow required notification permissions if you want completion alerts.
5. Keep upstream Antigravity and Antigravity Dev installed if desired: their Android package IDs are different.
6. To upgrade the fork, install a higher-`versionCode` APK signed with the **same permanent KR release certificate**. Do not uninstall the fork to update it.

## Known limitations and follow-up

- Head-up notification vibration may depend on Android's notification-channel settings, system policy and user preferences. A missing vibration was observed, but its cause has not been established.
- The actual five-second queue delay between *two nearly simultaneous real Core completions* remains an optional live test; deterministic FIFO tests passed.
- Long user prompts may appear visually shortened or collapsed; whether this is intentional upstream behavior remains under investigation. It was **not** established as a WebView freeze.
- The present upstream-style read/unread behavior is unchanged. **Seeing a response is not automatically treated as proof of consciously reading it.** A new model is deferred for product design and separate acceptance.
- No GitHub-hosted CI results are claimed for this manually built release.
